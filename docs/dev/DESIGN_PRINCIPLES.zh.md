# 设计思想(pi-tree 定制版)

> 本文档记录本项目的设计思想与关键决策,是开发计划的方法论依据。
> 配套文档:用户场景见 `USER_SCENARIOS.zh.md`,开发计划见 `DEV_PLAN.zh.md`。

---

## 一、继承自 pi-tree 的设计哲学

### 1. 对话是树,不是线程
人的理解过程天然是分叉的:读到一处不懂 → 岔开去查背景 → 弄懂 → 回到原处继续。
线性聊天把所有岔路堆进同一条上下文,50 条之后模型开始丢线、跑题、幻觉。
pi-tree 把每个回答变成树节点,**每条分支只携带"根 → 当前节点"的路径上下文**:
- 更少的噪音 → 更准的回答;
- 5 条 × 10 层的树只发约 10 条消息,而不是 50 条(省 token、省成本);
- 上下文污染是幻觉主因之一,隔离分支让模型始终被原文"锚定"。

### 2. Agentic,而非 RAG
向量检索是"近似相关",不是"精确命中"。
pi-tree 给 AI **工具**而非检索结果:按行号读原文(`read` 工具 + toc.json 行号导航),
像 `grep` 一样按需精确取上下文。本项目的划词提问进一步强化这一点——
**用户的选择就是最精确的上下文**。

### 3. Local-first,自带密钥
无云账号、无遥测。数据在本机(本项目部署在 SSD),密钥只存本地、只发给所选 provider。

## 二、本项目的增量设计思想

### 1. 复用而非重造
book 插件已实现"上传 → 处理管道 → 章节目录(带行号)→ 面板按章节显示原文 → 划词"的完整链路。
paper 插件 90% 照此模式,只新增"论文级章节提取"与"真 PDF 渲染"两块。**能抄的绝不重写。**

### 2. 改动边界 = 插件层 + 表现层
Pi SDK 是外部依赖,树模型/会话引擎在框架层。所有改动:
- paper 插件的工具/处理器/UI(插件层);
- 客户端 SettingsModal、PDF 面板、语言偏好(表现层);
- 服务端的 settings 写接口与文件服务(新增路由,不改核心逻辑)。

这样上游(shuowu/pi-tree)每次更新,合并冲突最小,fork 可以长期存活。

### 3. 真 PDF 渲染:嵌入开源方案 pdf.js
- 选 **pdfjs-dist**(Mozilla,Apache-2.0):Canvas 页面渲染 + 自带 TextLayer 文本层(原生可选中/复制/搜索),与 AGPL 兼容;
- 拒绝"整包 viewer 塞 iframe":选择事件跨 iframe 捕获割裂,划词工具栏无法无缝接入;
- 文本层 = 划词的根基:SelectionToolbar 监听容器内选择,选区映射为 `{页码, 原文, 章节}` 元数据注入提问;
- 扫描版(无文本层)显式降级提示,不做 OCR(明确非目标)。

### 4. 一份原文,双层索引
同一个 paper 源维护两套索引,分别服务两个"读者":
| 索引 | 形态 | 服务对象 | 用途 |
|---|---|---|---|
| 行号索引 | `toc.json`(`[{line, level, title}]`) | AI(agentic read) | 按行号精确引用原文作答 |
| 页码索引 | PDF 内嵌 outline(客户端 `doc.getOutline()`) | 人类(渲染面板) | 章节树跳页、定位 |

AI 的"行号世界"与用户的"页码世界"通过章节标题对齐,不必强求页码一致性。

### 5. 选择即上下文
划词提问的引用格式:`> 原文摘录` + 页码/章节 + 首句摘录。
开分支时引用原文,保证新分支的根节点自带精确锚点——树结构 + 精确引用 = 双保险。

### 6. 语言策略分层,不做全站 i18n
全站中文界面是 5 万行硬编码文案的大工程,已确认**不做**。
"AI 回复语言可选"用三层解决,成本约 1 天:
1. **模型层**:DeepSeek / glm / Qwen 中文能力天然足够;
2. **指令层**:skill 语言策略("按用户偏好语言作答,术语保留英文原文");
3. **偏好层**:设置页语言偏好注入 systemContext,会话内可临时覆盖。
只新增一个下拉控件,不碰全站文案。

### 7. 密钥安全:只进 models.json
- API Key **只写入** `$DATA_PATH/models.json`(不写 global-config.json,避免覆盖优先级坑);
- 接口只回显尾 4 位掩码,日志脱敏,落盘 0600;
- 写入后走现有缓存失效机制,新会话立即生效;
- 用户全程不碰 `.env`。

### 8. local-first 的部署形态
仓库与数据都放 SSD(外接盘),不占内置盘;Docker/源码/桌面均可,数据目录独立可迁移。

### 9. 锚点是第一公民(为 Zotero 第二阶段铺路)
每个提问节点除了问答内容,还携带**原文锚点** `anchor: { page, quote, section }`(页码 + 选中原文 + 章节)。
- 点击历史节点 = 恢复该分支问答上下文 **+ 跳回 PDF 对应页并高亮原文**——"回到上一层"从"看聊天"升级为"回到原文";
- 锚点与消息并列存放,不侵入 Pi SDK 树模型,便于导出;
- 阅读记录从第一天就是**可移植 JSON**(平铺 nodes 数组,Pi SDK 树 ↔ 数组双向映射),pi-tree 与未来的 Zotero 插件读同一份记录,**不需要迁移聊天历史**。

### 10. 核心 / 适配两层架构,pi-tree 是验证平台
路线分两阶段:**第一阶段在 pi-tree 上验证"对话树 + PDF 锚点"产品逻辑;第二阶段把核心能力拆成独立共享模块,做 Zotero 原生插件**——不是把 pi-tree 的 Electron 应用硬塞进 Zotero(运行环境不同)。
- 核心层(树模型、分支、锚点、上下文组装、记录读写)在第一阶段就按"独立可复用"的接口边界收敛;
- 适配层各管各的:pi-tree 适配层 = PDF 面板 + Session Tree + 本地库;Zotero 适配层 = Zotero PDF Reader + notes/annotations + 插件 SQLite;
- **许可边界**:直接复用 pi-tree 代码须遵守 AGPL-3.0(开源义务);第二阶段若独立重写核心、只复用接口设计与思路,边界更清晰。

## 三、关键决策记录

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 对话形态 | 沿用树状会话(原生) | 追问/返回上层是第一性需求,零开发 |
| 2 | 原文展示 | 真 PDF 渲染(pdfjs-dist) | 用户明确必做;原版排版 + 文本层可划词 |
| 3 | 章节结构 | 行号 toc.json + PDF outline 双索引 | AI 与人类各取所需,不强行统一 |
| 4 | 划词提问 | 复用 SelectionToolbar 扩展 meta | 基础设施已在,PDF 文本层兼容 |
| 5 | 中文支持 | 只做回答语言可选,不做全站 i18n | 用户确认;成本 1 天 vs 4-6 天 |
| 6 | 模型默认 | DeepSeek(deepseek-v4-flash) | 便宜、中文强、README 官方推荐 |
| 7 | 密钥配置 | 设置页 UI + models.json,默认 DeepSeek | 用户不改配置文件;掩码 + 0600 |
| 8 | 上游策略 | fork + 定期 rebase,改动留插件/表现层 | 吃上游修复,冲突最小,可选 PR 回馈 |
| 9 | 文件服务 | serveStatic Range(206) | pdf.js 分块加载必需,Hono 已内置 |
| 10 | 扫描版 PDF | 降级提示,不做 OCR | 明确非目标,避免暗坑 |
| 11 | 节点锚点 | 每个提问节点存 {page,quote,section},点击跳回 PDF | "回到上一层"升级为"回到原文";Zotero 第二阶段复用 |
| 12 | 阅读记录格式 | 可移植平铺 nodes JSON,Pi SDK 树↔数组双向映射 | pi-tree 与 Zotero 读同一份记录,免迁移 |
| 13 | 第二路线 | pi-tree 验证 → 拆核心 → Zotero 插件(不搬 Electron) | 运行环境不同;许可边界清晰 |
